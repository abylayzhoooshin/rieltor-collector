# rieltor-collector (Алматы)

Микросервис сбора и очистки объявлений аренды с krisha.kz (Алматы).
Собирает данные, чистит, убирает дубли и публикует готовый baseline по
HTTP — его забирает отдельный бот-оценщик.

Форк астанинского сборщика: архитектура 1:1 та же, поменян город
(`CITY = "almaty"` в `v2_krisha_pars_fixed.py`), геозона и алиасы города
в санитарном фильтре (`ALMATY_LAT_RANGE/LON_RANGE`, `CITY_ALIASES` в
`build_baseline.py`). Приведение цен по индексу (`price_index.py`) для
Алматы не откалибровано (ряд БНС был только по Астане) — модуль не
используется в этом деплое, пока не заведён реальный ряд под Алматы.

Один процесс = сбор по расписанию + HTTP API одновременно (`service.py`).

## Быстрый старт

```bash
pip install -r requirements.txt
python service.py                 # сбор + API на :8001
```

Проверка:

```bash
curl http://localhost:8001/health
curl http://localhost:8001/baseline/meta
```

## Структура

| Файл | Назначение |
|---|---|
| `service.py` | Точка входа: оркестратор + FastAPI в одном event loop |
| `orchestrator.py` | Расписание: full scan раз в 1ч, fast track раз в 5 мин |
| `v2_krisha_pars_fixed.py` | Полный обход (slow track): список страниц + детальные карточки; общий сетевой слой (curl_cffi) |
| `fast_track.py` | Быстрый обход первых страниц для свежих объявлений |
| `master_db.py` | SQLite-реестр: схема, апсерты, история цен |
| `paths.py` | Единая точка, где решается, куда писать состояние |
| `build_baseline.py` | Фильтр + дедуп + публикация версии baseline |
| `build_candidates.py` | Immutable pre-dedupe snapshot для Cleaner |
| `dedupe_baseline.py` | Поиск дублей (блокинг + правила + кластеризация) |
| `price_index.py` | Приведение цен во времени по официальному ряду |
| `official_rent_index.json` | Ряд БНС (конфигурация, правится руками) |
| `baseline_api.py` | Legacy HTTP, Mainrieltor event feed и version-pinned `/baseline/candidates/*` |
| `validate_candidate_migration.py` | Двойная проверка миграции на SQLite online backup |
| `seed_baseline.py` | Разовая заливка исторического CSV в базу |

## Ключевые решения

**Три слоя данных.** `master_db.listings` — полный архив, из него ничего
никогда не удаляется (снятые объявления получают `status='missing'`).
`baseline_<version>.db` — то, что отдаётся боту: только активные, после
фильтра и дедупа. `candidate_<version>.db` — независимый
согласованный active+missing snapshot до business-фильтра и дедупа.
Он содержит listings, ordered photos, price observations, presence
events и manifest с totals/SHA-256. Presence пишется только на переходах
`first_seen`, `missing_confirmed`, `reactivated`; повторное наблюдение active
обновляет `last_seen_at`, но не создаёт `seen` на каждое объявление.

**Неизменяемые версии baseline.** Файл версии никогда не переписывается
после создания, публикация — через атомарную подмену маленького
`latest.json`. Поэтому гонка «сборщик пишет / API читает» невозможна
структурно, а не «пока везёт».

**Всё состояние — в `DATA_DIR`.** На проде это persistent disk. Без этого
`orchestrator_state.json` и `fast_known_ids.json` обнулялись бы при
каждом редеплое, и fast track считал бы все объявления новыми.

**Цена в базе не мутирует.** Приведение во времени — производная
величина, считается на чтении через `price_index.factor()`. Источник
под этой функцией можно менять, не трогая вызывающий код. Сейчас
приведение фактически не применяется: в baseline попадают только
активные объявления, у них цены уже текущие. Модуль нужен на момент,
когда в пул пустят снятые.

**Сборщик выглядит как один браузер.** Оба воркера ходят через
curl_cffi с отпечатком Chrome (`IMPERSONATE`), порядком заголовков как у
Chrome и Referer'ом, как при кликах по ссылкам. Куки общие и переживают
рестарты (`krisha_cookies.json` в `DATA_DIR`). Любой 4xx кроме 404/410 или
страница SafeLine — блокировка: прогон сразу прерывается, куки
сжигаются, ответ сайта сохраняется в `full_blocked_last.html` /
`fast_blocked_last.html`, и оркестратор не пускает воркеров на сайт
`BLOCKED_COOLDOWN_MIN` минут. Страница без карточек или несколько карточек
подряд без `window.data` — смена разметки, прогон тоже прерывается, чтобы
не засчитывать поломку сайта как брак объявлений.

**Пропажа подтверждается двумя обходами.** Объявление помечается
снятым, только если его не видели дольше `MISSING_GRACE_S`. Список на
krisha отсортирован по дате, новые объявления сдвигают остальные вниз,
и за время обхода строка может уехать на следующую страницу — без
отсрочки такие объявления мигали бы active/missing каждый цикл.

**Параллельный сбор.** Полный обход и fast track имеют независимые
расписания: fast track продолжает работать каждые 4–6 минут, даже если
полный обход ещё не закончен. Второй экземпляр того же обхода не запускается.
В режиме `all` каждая прочитанная страница сразу обновляет цены в базе
и передаёт новые/неполные карточки и очередь обновления фото обработчику.
Карточки загружаются и сохраняются по одной, пока продолжается чтение
следующих страниц. Отметка `missing` по-прежнему разрешена только после
полного свежего обхода списка.

Все задачи используют общую очередь HTTP-запросов `RequestGate`:
одновременно идёт один запрос, после него выдерживается пауза
`LIST_DELAY_MIN/MAX` или `DETAIL_DELAY_MIN/MAX`. Поэтому параллельная
работа задач не складывает их частоты запросов. Это обеспечивает раннее
появление данных и работу fast track во время полного обхода, но не
обещает ускорить весь обход. Любая блокировка закрывает сетевой доступ
всем задачам на общий cooldown. Время наблюдения защищает цены и карточки
от перезаписи более старыми результатами другой задачи.

**Событийный лог для внешних потребителей.** `master_db.listing_events` —
курсорный журнал "new"/"price_drop", который пишут ОБА сборщика при
апсерте (см. `master_db.upsert_full`/`record_price_changes`), а не только
fast track: иначе события, замеченные full scan'ом вне узкого окна fast
track, терялись бы. "new" фиксируется только для объявлений, реально
опубликованных на krisha недавно (`created_at`, порог —
`NEW_LISTING_MAX_AGE_DAYS`) — иначе докачка долга старых карточек full
scan'ом выглядела бы как лавина "новых" объявлений. Отдаётся по
`/listings/changes?since=<event_id>` — курсор, а не время, поэтому
потребитель, опросивший сервис позже обычного, не теряет события.

При снижении цены карточка с `scraped_at` старше 24 часов (или без
читаемой даты) загружается повторно: обновляются `photo_urls`, `photo_count`
и `photo_set_hash`. Порог задаёт `PRICE_DROP_DETAIL_MAX_AGE_HOURS`.
Fast track сначала пробует загрузить карточку, затем сохраняет её вместе
с событием. Если загрузка не удалась, цена и событие сохраняются сразу,
а обновление остаётся в SQLite (`detail_refresh_queue`) до успешной загрузки.
Очередь подхватывают fast track в своём окне и full scan в своём списке;
для неполных карточек действует существующий лимит `MAX_FETCH_ATTEMPTS`.
При сетевых сбоях лимит не расходуется. Полный обход может опубликовать
событие раньше, чем закончится загрузка фотографий. Повторное обновление
фото не создаёт второго `price_drop`: потребителю после `photos_unavailable`
нужно повторно запросить `/listings/{id}`. Уже обработанные до внедрения
события автоматически не переигрываются.

Локальные проверки без обращений к Krisha:
`python -m unittest discover -v`.
Файлы тестов не запускаются при обычном старте сервиса на Render.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATA_DIR` | `.` | Каталог состояния (на проде — точка монтирования диска) |
| `KRISHA_DB` | `$DATA_DIR/krisha_almaty.db` | Явный путь к базе, перебивает `DATA_DIR` |
| `BASELINE_DIR` | `$DATA_DIR/baseline_versions` | Куда публиковать версии baseline |
| `CANDIDATE_DIR` | `$DATA_DIR/candidate_versions` | Отдельный каталог candidate versions |
| `CANDIDATE_KEEP_VERSIONS` | `2` | Сколько candidate DB сохранять (минимум 2) |
| `BASELINE_API_KEY` | пусто | Токен для `/baseline/*`. **Пусто = проверка выключена** |
| `BASELINE_API_PORT` | `8001` | Порт HTTP |
| `BASELINE_BUILD_INTERVAL_MIN` | `30` | Как часто пересобирать baseline |
| `CANDIDATE_BUILD_INTERVAL_MIN` | `30` | Независимый таймер candidate snapshot; без сети |
| `BASELINE_STALE_AFTER_S` | `14400` | Возраст, после которого `/health` отдаёт 503 |
| `BASELINE_STARTUP_GRACE_S` | `14400` | Сколько ждать первого baseline на пустом диске |
| `BASELINE_MAX_SHRINK` | `0.25` | Допустимое сокращение baseline; больше — отказ публиковать |
| `FULL_SCAN_INTERVAL_H` | `1` | Интервал full scan (среднее; реальный момент — в диапазоне `FULL_SCAN_INTERVAL_H_MIN..MAX`, по умолчанию 0.9–1.1ч, то есть 54–66 минут) |
| `FAST_INTERVAL_MIN` | `5` | Интервал fast track (среднее; реальный момент — `FAST_INTERVAL_MIN_MIN..MAX`, по умолчанию 4-6мин) |
| `BLOCKED_COOLDOWN_MIN` | `90` | Пауза всего сбора после блокировки антиботом |
| `MISSING_GRACE_S` | `21600` | Сколько не видеть объявление, прежде чем пометить снятым |
| `NEW_LISTING_MAX_AGE_DAYS` | `1` | Насколько недавно объявление должно быть опубликовано на krisha, чтобы событие "new" засчиталось |
| `PRICE_DROP_DETAIL_MAX_AGE_HOURS` | `24` | Возраст карточки, начиная с которого снижение цены требует обновления карточки и фотографий |
| `OFFICIAL_INDEX_PATH` | рядом с кодом | Путь к ряду БНС |
| `LOG_LEVEL` | `INFO` | Уровень логирования |

## Заливка существующей базы

Если есть исторический CSV, его можно влить один раз:

```bash
python seed_baseline.py --csv krisha_astana_baseline.csv --dry-run
python seed_baseline.py --csv krisha_astana_baseline.csv
```

Строки заливаются со `status='missing'` — подтвердить, что объявление
ещё живо, может только обход сайта. Первый же full scan поднимет живые
в `active`, мёртвые останутся в архиве и в baseline не попадут.

## Деплой на Render

Репозиторий содержит `render.yaml` (Blueprint). Dashboard → New →
Blueprint → указать репозиторий. Диск создастся автоматически.

Важно: нужен **платный** план. Free-инстансы засыпают через 15 минут без
HTTP-трафика (сборщик должен работать в фоне), и к ним нельзя
прикрепить persistent disk.

## Обновление ряда цен

`official_rent_index.json` правится вручную раз в месяц. Источник:
stat.gov.kz → Статистика цен → Электронные таблицы → «Индексы цен и цены
на рынке жилья», строка по г. Астана, аренда благоустроенного жилья.
Код менять не нужно — только JSON.

## Доступ к API

`/health` различает три состояния: `starting` (200 — baseline ещё ни разу
не собирался, идёт первичное наполнение; перезапуск не поможет, поэтому
не 503), `ok` (200), `stale`/`broken` (503 — здесь перезапуск уместен,
платформа его и сделает).

`/baseline/meta`, `/baseline/table`, `/baseline/candidates/*`, `/price-index` требуют заголовок
`X-API-Key`, если задан `BASELINE_API_KEY`. `/health` открыт всегда —
иначе платформа не сможет проверять сервис.

`/baseline/table` отдаёт страницами: `limit` по умолчанию 100, максимум
500. Полную таблицу забирают постраничным обходом, сверяясь с `total` и
`version` в ответе; если версия сменилась посреди обхода, страницы
относятся к разным наборам данных и обход надо начать заново.

Candidate client сначала читает `/baseline/candidates/meta`, затем
передаёт его `version` в `/listings`, `/photos`, `/prices` и `/presence`.
Контракт `candidate-v2` публикует
`hash_algorithm=sha256-canonical-jsonl-v1`; `listings_sha256` считается по
публичным строкам с восстановленным `photo_urls`, поэтому все hashes можно
независимо проверить только через HTTP (точная канонизация описана в
`ALMATY_COLLECTOR_ENTITY_HANDOFF.md`).
Удалённая retention-политикой version отвечает HTTP 410; fallback на
текущую версию запрещён.

`/listings/changes?since=<event_id>&limit=<n>` — курсорный поток новых
объявлений (`reason=new`) и подешевений (`reason=price_drop`) из живого
`master_db`, а не из версионированного baseline. Первый запрос —
`since=0`. Каждый ответ содержит `next_since`; если `count` в ответе
равен `limit`, скорее всего есть ещё, и нужно повторить запрос с
`since=next_since`. `limit` по умолчанию 200, максимум 500.

`/listings/{id}` — текущая полная карточка объявления из `master_db`
(площадь, комнаты, адрес и т.п.), не дожидаясь следующей публикации
baseline. 404, если id не найден.

## Что ещё не сделано

- `seller_type` пустой у 100% строк — баг парсера (`owner.get("type")`
  не существует в `window.data`)
- Нет решения JS-челленджа SafeLine: блокировка распознаётся и пережидается,
  но не обходится. Счётчик `fetch_failures` не затухает — объявления, чьи
  карточки по-настоящему неполные, после 4 попыток выпадают из перекачки
  навсегда
- Флаг остановки не доходит до воркеров: SIGTERM не прерывает уже
  идущий обход, платформа добивает процесс по таймауту
- Нет `/metrics`
- ИИ-разметка (red flags, оценка ремонта) — отдельным сервисом поверх
  готового baseline, в этот репозиторий не входит
